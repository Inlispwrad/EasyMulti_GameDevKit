# EasyMulti リレーを自分で立てる

**[English](en.md) · [中文](zh.md) · 日本語**

このドキュメントは、**サーバーを立てたことが一度もない方**を想定しています。各ステップで「このコマンドは何をしているのか」「正常なら何が表示されるのか」「違うものが出たらどうするか」を説明します。所要時間はおよそ 30 分です。

---

## 用意するもの

| | |
|---|---|
| Linux サーバー 1 台 | クラウドはどこでも構いません（AWS、さくら、ConoHa、Alibaba Cloud、Hetzner…）。1 vCPU / メモリ 1 GB で十分です。リレーは軽量で、このマシン上でコンパイルは一切行いません |
| その**グローバル IP アドレス** | クラウドのコンソールのインスタンス詳細に表示されています |
| ログイン手段 | 作成時に設定した root パスワード、またはアップロード済みの SSH 鍵 |

ドメインは**不要**、Docker の知識も**不要**、サーバーへの .NET インストールも**不要**です。ドメインが要るのは**ブラウザ**からプレイヤーを接続させたい場合だけです（[最後の節](#任意-ブラウザからも繋げるようにする-httpswss)を参照）。

---

## まず、何を入れようとしているのかを把握する

リレーは**ひとつのプロセス**で、やることは 3 つだけです。認証、ルーム管理、メッセージの転送。特徴は次のとおりです。

- **同じポート番号で 2 系統**を待ち受けます。TCP（ブラウザ向けの WebSocket）と UDP（デスクトップ／コンソール向け）で、既定はどちらも `7777` です。TCP と UDP は独立したプロトコルスタックなので、同じ番号を共有できます。
- **データを一切保存しません。** データベースもディスク書き込みもなく、再起動すればすべてのルームが消えます。つまり不調なら再起動するだけで済み、失われるものはありません。
- **ゲームロジックは動かしません。** 誰がホストか、ダメージ計算をどうするかは、すべてあなたのゲーム側の話です。

ですから全体像はこれだけです。**プロセスを起動する → ポートを 2 つ開ける → パスワードを渡す。**

## ステップ 1：サーバーに接続する

SSH は Linux サーバーにリモートログインする標準的な方法です。自分の PC でコマンドを打ち、実際にはサーバー上で実行されます。

**Windows**（PowerShell か CMD、Win10 以降は標準搭載）でも **macOS／Linux**（ターミナル）でも同じコマンドです。

```bash
ssh root@サーバーのIP
```

クラウド側のユーザー名が `root` でない場合（AWS では `ubuntu` や `ec2-user`、Alibaba Cloud の一部イメージでは `admin`）は、`root` をそれに置き換えてください。

初回は `Are you sure you want to continue connecting?` と聞かれるので、`yes` と入力して Enter。続いてパスワードを入力します。**入力中は画面に何も表示されませんが、これは正常です。** 入力し終えたら Enter を押してください。

`root@server:~#` のようなプロンプトが出れば、サーバーにログインできています。以降のコマンドはすべてここで実行します。

> **繋がらないときは？** まず IP の写し間違いを確認します。次にクラウドのファイアウォールで **22 番ポート**が許可されているか確認してください（ほぼすべてのクラウドで既定で許可されています）。パスワードを何度も間違えると一時的にロックされることがあるので、数分待ちましょう。

---

## ステップ 2：Docker を入れる

Docker を使うと、サーバーに .NET を入れる必要も、コンパイルする必要も、依存関係を管理する必要もなくなります。リレーはビルド済みイメージとして配布しているので、起動するだけです。

```bash
curl -fsSL https://get.docker.com | sh
```

これは Docker 公式のインストールスクリプトで、ディストリビューションを自動判別します。1〜2 分で終わります。確認しましょう。

```bash
docker --version
```

`Docker version 2x.x.x, build ...` と出れば成功です。

> **`curl: command not found` と出たら？** 先に入れます。Ubuntu／Debian なら `apt update && apt install -y curl`、CentOS／RHEL 系なら `yum install -y curl`。
>
> **permission denied と出たら？** root ではありません。コマンドの前に `sudo` を付けるか、先に `sudo -i` で root になってください。

## ステップ 3：トークンを生成する

トークンはこのリレーの**入館パスワード**です。**決めるのはあなた自身**で、サーバーが発行してくれるものではありません。ランダムな文字列を生成し、片方をリレーに、同じものをゲームクライアントに設定します。両者が一致して初めて接続できます。

```bash
openssl rand -hex 32
```

64 文字の 16 進文字列が表示されます。**安全な場所に控えておいてください。** ステップ 4 とステップ 8 で同じ値を使います。

> **サーバーに `openssl` がない場合は？** どの Linux でも動くこちらを使ってください。
>
> ```bash
> head -c 32 /dev/urandom | od -An -tx1 | tr -d " \n"; echo
> ```

⚠️ この文字列はパスワードです。git リポジトリにコミットしたり、公開の場に貼ったりしないでください。

---

## ステップ 4：リレーを起動する

`あなたのトークン` の部分をステップ 3 の文字列に置き換えてください。

```bash
docker run -d --name easymulti --restart unless-stopped -p 7777:7777/tcp -p 7777:7777/udp -e EASYMULTI_TOKEN=あなたのトークン ghcr.io/inlispwrad/easymulti-relay:latest
```

**各オプションの意味**は一度目を通しておく価値があります。トラブル時に効いてきます。

| オプション | 役割 |
|---|---|
| `-d` | バックグラウンド実行。付けないとターミナルが占有されたままになります |
| `--name easymulti` | コンテナに名前を付けます。以降の `docker logs easymulti` などで使います |
| `--restart unless-stopped` | **サーバー再起動後に自動で立ち上がり**、プロセスが落ちても再起動します。これを忘れると、マシンを再起動した時点でリレーが消えます |
| `-p 7777:7777/tcp` | サーバーの TCP 7777 番をコンテナに割り当てます。ブラウザ側はこちらを使います |
| `-p 7777:7777/udp` | 同じく UDP。**デスクトップ側はこちらで、最も忘れられやすいのがこれです** |
| `-e EASYMULTI_TOKEN=...` | トークンを渡します。**これがないとリレーは起動を拒否します。** 無防備なまま動かさないための意図的な仕様です |
| `ghcr.io/...:latest` | 実行するイメージ。初回は自動でダウンロードされます（約 110 MB） |

実行すると長い 16 進文字列が表示されます。これはコンテナ ID で、**起動指示が受け付けられた**ことを意味します。ただし「動いている」という意味ではないので、次で確認します。

---

## ステップ 5：本当に動いているか確認する

3 段階で見ます。どこで止まっているかがそのまま原因の切り分けになります。

### ① コンテナは動いているか

```bash
docker ps
```

1 行表示され、`STATUS` 列が `Up X seconds` になっていれば OK です。

> **一覧が空**なら、起動直後に終了しています。慌てず、次のコマンドで理由を確認しましょう。

### ② 何を出力しているか

```bash
docker logs easymulti
```

正常な起動ログはこうなります。

```
[EasyMulti] Starting: token=configured
[EasyMulti] WebSocket: port 7777
[EasyMulti] UDP:       port 7777
[EasyMulti] WebSocket listening on ws://+:7777/
[EasyMulti] UDP listening on udp://0.0.0.0:7777
```

重要なのは最後の 2 行で、両方のチャネルが待ち受けていることを示します。

> **「トークンがない」と出たら？** ステップ 4 の `-e EASYMULTI_TOKEN=` が空か、貼り付け時に切れています。`docker rm -f easymulti` で削除してやり直してください。

### ③ サーバー自身から繋がるか

```bash
curl http://localhost:7777/health
```

`ok` と返れば正常です。

ここまでで**リレー自体には問題がありません**。ただし外部からはまだ届きません。クラウドのファイアウォールが既定で閉じているためです。

## ステップ 6：ポートを開ける（最もつまずきやすい所）

ここに落とし穴があります。**ファイアウォールは 2 層あります。**

| | 場所 | 触る必要は？ |
|---|---|---|
| **クラウド事業者のファイアウォール** | クラウドの管理画面（Web） | **あります。** 既定では 22 番など一部しか通しません |
| OS のファイアウォール（ufw / firewalld） | サーバーの中 | 通常**ありません。** Docker はポート公開時に自身で iptables ルールを書き、大抵はこれを迂回します |

つまり、**サーバーの中でファイアウォールを探さず、クラウドの管理画面を開いてください。**

**ポート番号は同じでプロトコルが違う**ルールを 2 本追加します。

| プロトコル | ポート | 用途 |
|---|---|---|
| **TCP** | 7777 | ブラウザ／WebSocket クライアント、ヘルスチェック |
| **UDP** | 7777 | Godot や Unity などのデスクトップクライアント |

**忘れられやすいのは UDP のほうです。** しかも症状が紛らわしく、ブラウザは繋がりヘルスチェックも通るのに、デスクトップだけが繋がりません。

主なクラウドでの場所：

- **AWS EC2 ／ Alibaba Cloud ECS ／ Tencent Cloud CVM**：「ファイアウォール」ではなく**セキュリティグループ**を探します → インバウンドルールを編集 → 追加。ポート範囲 `7777`、送信元 `0.0.0.0/0`。
- **Alibaba Cloud 軽量アプリケーションサーバー**：コンソール → インスタンスを開く → **ファイアウォール**タブ → ルール追加 →「カスタム」を選び、TCP/7777 と UDP/7777 を個別に追加します。「全 TCP+UDP」のようなテンプレートは全ポートを開けてしまうので選ばないでください。
- **さくらのクラウド／ConoHa／DigitalOcean など**：「パケットフィルタ」「セキュリティグループ」「Firewalls」といった項目から受信ルールを追加します。

ルールは通常すぐ反映され、サーバーの再起動は不要です。

---

## ステップ 7：外から確認する（2 系統を別々に）

**自分の PC に戻って**（サーバー上ではありません）、IP を自分のものに置き換えて実行します。

### TCP の確認

```bash
curl http://サーバーのIP:7777/health
```

`ok` が返れば TCP は開通しています。

> **タイムアウトする／繋がらない場合は？** ステップ 6 の TCP ルールが効いていません。ポート番号、プロトコルが TCP になっているか、**インバウンド（受信）**方向か、保存したかを見直してください。

### UDP の確認

UDP はコネクションレスなので、**curl では確認できず、ヘルスチェックもありません。** リポジトリの Echo サンプルで実際に叩きます（自分の PC に [.NET 8 SDK](https://dotnet.microsoft.com/download) が必要です）。

```bash
git clone https://github.com/Inlispwrad/EasyMulti_GameDevKit.git
cd EasyMulti_GameDevKit
dotnet run --project examples/Echo -c Release -- --mode host --name Probe --transport udp --relay-host サーバーのIP --token あなたのトークン
```

ルームコードが表示されれば **UDP も開通**しており、トークンも転送経路も正常です。`Ctrl+C` で終了します。

> **止まったままでルームコードが出ない場合は？** UDP ルールが効いていないか、トークンが違います。トークンが誤っている場合は `bad_token` と表示されます。

両方通れば、**サーバー側は完了**です。

## ステップ 8：ゲームから接続する

ゲームプロジェクト側で設定します（SDK の導入方法は [USAGE.md](../USAGE.md) を参照）。

```csharp
EasyMulti.Init(new()
{
    Token     = "ステップ 3 で生成した文字列",
    GameId    = "my-game",          // ゲームの名前空間。gameId が違うルームは互いに見えません
    RelayHost = "サーバーのIP",
    RelayPort = 7777,
    Codec     = new MemoryPackCodec(),
});
```

サーバーと一致させる値は 3 つです。**トークンは一字一句同じ**、IP はサーバーのグローバル IP、ポートは 7777。

クライアントを 2 つ起動し、片方でルームを作成、もう片方でルームコードから参加します。双方向にメッセージが届けば、経路全体が通っています。

## 任意：ブラウザからも繋げるようにする（HTTPS/wss）

この節が必要なのは、**Web 版を出す場合**（Godot／Unity の Web エクスポートを含む）だけです。デスクトップやモバイルには不要です。

理由はブラウザの安全規則です。HTTPS ページからは `wss://`（暗号化された WebSocket）**しか**開けず、平文の `ws://` は混在コンテンツとして遮断されます。そして証明書の発行には**ドメイン**が必要です。Let's Encrypt は IP アドレスだけでは証明書を発行しないため、ここだけはドメインを避けて通れません。

1. **ドメインを取得**し、サーバーのグローバル IP を指す **A レコード**を追加します（例：`relay.yourgame.com`）。
2. クラウドのファイアウォールで **80/TCP と 443/TCP** も開けます。80 番は証明書の検証に使うため、443 だけでは発行できません。
3. サーバーに 3 つのファイルを置きます。

```bash
mkdir -p ~/easymulti && cd ~/easymulti
curl -O https://raw.githubusercontent.com/Inlispwrad/EasyMulti_GameDevKit/main/deploy/docker-compose.yml
curl -O https://raw.githubusercontent.com/Inlispwrad/EasyMulti_GameDevKit/main/deploy/Caddyfile
printf 'EASYMULTI_TOKEN=あなたのトークン\nEASYMULTI_TAG=latest\n' > .env
```

4. `Caddyfile` のドメインを自分のものに置き換えます。

```bash
sed -i 's/yourgame.example.com/relay.yourgame.com/' Caddyfile
```

5. ステップ 4 のコンテナを停止し、この構成に切り替えます。Caddy が証明書の取得と更新を自動で行います。

```bash
docker rm -f easymulti
docker compose up -d
```

6. クライアント側を変更します。

```csharp
RelayHost = "relay.yourgame.com",
RelayPort = 443,
Transport = EasyMultiTransport.Wss,
```

**ひとつ明確にしておきます。** TLS が守るのは WebSocket 側だけです。UDP は HTTP リバースプロキシを通せないため、デスクトップのプレイヤーは引き続き 7777/udp に平文で直接接続します。ひとつのルームに暗号化されたブラウザプレイヤーと平文のデスクトッププレイヤーが同居することになりますが、これは不具合ではありません。ただし「wss にしたから全経路が暗号化されている」とは考えないでください。

## 日々の運用

```bash
docker logs -f easymulti        # ログをリアルタイム表示（Ctrl+C で抜けてもリレーは止まりません）
docker restart easymulti        # 再起動
docker stop easymulti           # 停止
docker start easymulti          # 再開
```

**新しいバージョンへの更新：**

```bash
docker pull ghcr.io/inlispwrad/easymulti-relay:latest
docker rm -f easymulti
# そのうえでステップ 4 の docker run をもう一度実行します
```

compose 構成なら 2 コマンドで済みます。

```bash
docker compose pull && docker compose up -d
```

**再起動で何が失われますか？** すべてのルームと接続中のセッションです。リレーが状態を持たないのは設計上の意図です。クライアントには切断イベントが届くので再接続できますが、プレイ中の更新は避けましょう。

## トラブルシューティング

| 症状 | 原因 | 対処 |
|---|---|---|
| `docker: command not found` | Docker が入っていない | ステップ 2 をやり直す |
| `docker ps` が空 | 起動直後に終了している | `docker logs easymulti` で理由を確認 |
| ログに「トークンがない」 | `-e EASYMULTI_TOKEN=` が空か切れている | `docker rm -f easymulti` 後にステップ 4 をやり直す |
| サーバー上の `curl localhost` が失敗 | リレーが起動していない | ステップ 5 を参照 |
| ローカルは通るが外から通らない | **クラウドの TCP ルール** | ステップ 6 |
| ブラウザは繋がるがデスクトップは繋がらない | **クラウドの UDP ルール** | ステップ 6。プロトコルを UDP にすること |
| クライアントが `bad_token` | 両側のトークンが不一致 | 一字ずつ照合。余分な空白や改行の混入に注意 |
| クライアントが `name_taken` | 同じ playerId の接続が既にある | 別の名前にするか、旧接続のタイムアウト（最大 60 秒）を待つ |
| クライアントが `bad_game_id` | gameId が空、または不正な文字を含む | 英数字と `.` `-` `_` のみ、1〜64 文字 |
| ポートが使用中 | 7777 を他のプログラムが使っている | 別のポートへ：`-p 8888:7777/tcp -p 8888:7777/udp`。クライアント側も 8888 に |
| 再起動したらリレーが消えた | `--restart unless-stopped` の付け忘れ | そのオプションを付けてステップ 4 をやり直す |

## セキュリティの境界（必ずお読みください）

**トークンが防げるのはクローラーや無差別スキャンまでで、意図を持った相手は防げません。** これは免責文ではなく、設計上の必然です。

- トークンは**ゲームクライアントに埋め込まれます**。ゲームを解析されれば取り出せます。
- トークンを入手した人は、あなたのリレーに接続し、ルームを作成・参加できます。
- リレーは**ゲームデータの中身を解析しません**。したがって対戦内容の安全性は、あなたのゲームプロトコルの責任です。暗号化すべきものは暗号化し、権威ある判定はクライアントを信用せずホスト側で行ってください。

リレー自体は何も保存せずディスクにも書かないため、最悪の場合でも「帯域を使われる」までです。保持していないので、プレイヤーデータが漏れることはありません。

実際の金銭や機微な情報を扱うものを作る場合、この共有トークン方式では**不十分**です。ゲーム層で本物の認証を別途用意してください。
